# План рефакторинга JPEG Glitch Editor

Разбор основан на коммите `bf81eb9`. Область работы — внутреннее устройство
редактора. Контракт совместимости включает текущий интерфейс и поведение
инструментов, исходные байты JPEG, историю с Undo/Redo, маски и режимы экспорта.
Сохранение и открытие проекта используют актуальную схему `.jpglitch`. При
открытии файла `.jpglitch v1` допустима ошибка неподдерживаемой версии.

## Повторное использование состояния JPEG в Worker

### Текущий путь обработки

При изменении истории приложение заново собирает список активных JPEG-операций.
Предпросмотр добавляет к нему черновую операцию. Для каждого кодирования клиент
создаёт Worker, передаёт копию исходного JPEG, а кодек читает коэффициенты,
применяет весь список по порядку и пишет результат. Worker завершается после
ответа. Apply с параметрами готового предпросмотра повторяет расчёт.
Перестановка уже выключенной записи может запустить кодирование того же списка
активных операций из-за новой ссылки на массив.
[История](../src/operations/history.ts#L336) ·
[Предпросмотр](../src/App.tsx#L3111) ·
[Клиент кодека](../src/application/coefficient-reader.ts#L32) ·
[Worker](../src/jpeg/coefficient.worker.ts#L507)

Исходный замер сделан в Node на поставляемом WASM-модуле. Синтетический baseline
JPEG — 4000×3000, 4:2:0. Операция — инверсия AC в компоненте яркости. Приведены
медианы семи прогонов по этапам кодека.

| Стек                         | Чтение коэффициентов | Применение | Запись baseline JPEG |
| ---------------------------- | -------------------: | ---------: | -------------------: |
| 1 операция, маска 320×240    |                56 мс |     0,5 мс |                63 мс |
| 24 операции, маска 320×240   |                54 мс |      12 мс |                63 мс |
| 1 операция, всё изображение  |                56 мс |      48 мс |                66 мс |
| 24 операции, всё изображение |                58 мс |   1 153 мс |                68 мс |

Для маленьких масок больше всего времени занимает чтение и запись. Для длинных
стеков полноразмерных эффектов основная стоимость — повторное применение
предыдущих операций.

### Сначала убрать повторные запросы

- Формировать одну типизированную команду для Preview, Apply и Auto Apply. Для
  кодирования сравнивать исходный документ, порядок активных операций,
  параметры, содержимое масок, seed и режим записи. Идентичность плана вычислять
  при его изменении. Порядок выключенных записей влияет на историю, а в план
  кодирования входят только активные операции.
- При точном совпадении плана Preview и Apply использовать готовые байты или
  присоединиться к уже запущенному запросу. Закрепление результата проходит
  через обычную команду истории. Кэш байтов ограничить текущим результатом и
  актуальным черновиком. Статус браузерного декодирования хранить отдельно от
  байтов, доступных для экспорта.
- Убрать повторное создание одинаковых копий входа и выхода. Передавать Worker
  одну копию `ArrayBuffer` с передачей владения. `OriginalAsset` продолжает
  владеть исходными байтами для Reset и экспорта оригинала.
  [Хранилище исходника](../src/document/model.ts#L6) ·
  [Передача буфера](../src/application/coefficient-reader.ts#L127)
- Освобождать временный входной буфер в WASM сразу после `_coefficient_open`.
  C-мост уже скопировал вход в `state.input`. Чтение блоков освобождает
  временный буфер сразу, а кодирование держит его до конца расчёта. Один общий
  шаг открытия уберёт копию размером с исходник из дальнейших этапов. В прямом
  прогоне поставляемого WASM на 11 фикстурах результаты совпали побайтно для
  обоих режимов записи.
  [Кодирование и чтение](../src/jpeg/coefficient.worker.ts#L524) ·
  [Копирование в C-мосте](../src/jpeg/codec/coefficient-bridge.c#L235)

### Затем проверить повторное использование коэффициентов

- Прототипировать Worker на срок жизни документа. Сначала измерить отдельно
  выигрыш от повторного использования загруженного WASM. Текущий C-мост вызывает
  `jpeg_finish_decompress` при записи JPEG, поэтому одной смены жизненного цикла
  Worker для повторного использования коэффициентов недостаточно. Нужен явный
  жизненный цикл состояния кодека после записи.
  [C-мост](../src/jpeg/codec/coefficient-bridge.c#L809)
- Начать с одной контрольной точки для подтверждённого состояния. Она содержит
  квантованные DCT-коэффициенты и актуальные таблицы DQT в контексте исходной
  геометрии и метаданных. Apply новой операции и Preview используют точку, если
  её префикс совпадает с началом активного плана. То же правило действует при
  редактировании, выключении, удалении и переносе записей. Если префикс
  разошёлся, пересчитать из исходника. Черновик меняет рабочее состояние.
  Контрольная точка обновляется после успешного расчёта для текущего
  подтверждённого плана.
- При смене файла освобождать состояние предыдущего документа. Reset сбрасывает
  привязку контрольной точки к правкам. Проверять идентификатор документа и
  запроса перед публикацией результата. Пока WebAssembly занят синхронным
  вызовом, немедленная отмена возможна через завершение Worker и восстановление
  из исходника. В бюджет памяти включить коэффициенты, рабочие буферы и копии
  для кодирования. Одна копия коэффициентов для изображения из замера занимает
  около 34 МиБ. Исходные пределы — 256 МиБ на коэффициенты изображения и 512 МиБ
  для WASM-кучи. [Ограничение кодека](ARCHITECTURE.md#4-jpeg-engine-boundary)
- Проверить повторное использование обработанных коэффициентов при
  progressive-экспорте. Для небольших масок отдельно измерить обход только
  затронутых блоков. При этом сохраняются порядок обхода для seeded-операций,
  семантика порогов покрытия и размеры видимых крайних блоков. Scan Corrupt
  получает чистый закодированный результат через собственный Worker.
  [Обход блоков](../src/jpeg/codec/coefficient-bridge.c#L414) ·
  [Маска блоков](../src/jpeg/block-geometry.ts#L538)
- Отдельно замерить подготовку списка индексов DCT и констант до внутреннего
  цикла `coefficient_apply`. Сейчас режим, `u+v` и часть параметров вычисляются
  заново для коэффициентов. Сравнить значения и последовательность вызовов
  генератора с текущим обходом по строкам и индексам.
  [Внутренний цикл](../src/jpeg/codec/coefficient-bridge.c#L414)

### Критерии проверки

- Один вызов кодирования на один и тот же план в Preview → Apply.
  Автопредпросмотр следующего шага после Apply получает новый план. Ноль вызовов
  при перестановке уже выключенной записи. Изменение параметров, seed, маски или
  режима записи приводит к расчёту по новым данным.
- Сравнить полный и инкрементальный расчёт по квантованным коэффициентам, DQT и
  метаданным. Проверить повторяемость байтов в одном режиме записи при
  одинаковой версии кодека. Включить случайные операции с seed, DQT
  reinterpret/requantize, перестановку, Undo/Redo, grayscale, 4:2:0, 4:2:2,
  4:4:4, нечётные размеры, EXIF и progressive-вход и экспорт.
- Проверить быструю смену параметров, отмену, смену файла во время кодирования и
  открытие проекта из одних выключенных операций. Измерить в браузере время до
  отображения, работу Worker и пиковую память для коротких и длинных стеков.
  [Стратегия тестирования](JPEG_TEST_STRATEGY.md#10-performance-and-robustness)

## Упрощение архитектуры

### История и реестр операций

`createJpegDocumentSession` создаёт универсальные `OperationHistory<State>` и
`OperationRegistry<State>`. В приложении у обоих одна предметная модель —
`JpegEditableState`. Для обычного эффекта `registerGlitchOperation`
перепроверяет JSON и добавляет команду в массив. Исполняется она позже в Worker.
Метаданные `domain` и `requiresReencoding` хранятся в реестре. Решение о
кодировании зависит от массива команд. История также создаёт
JavaScript-генератор случайных чисел для каждой активной записи.
Зарегистрированные JPEG-операции его игнорируют, поскольку Worker передаёт seed
в кодек. [Реестр](../src/operations/schema.ts#L108) ·
[Регистрация JPEG-операций](../src/application/jpeg-document.ts#L109) ·
[Воспроизведение](../src/operations/history.ts#L336)

- Оставить реестру конкретную ответственность — распознать операцию по типу,
  проверить параметры и вернуть типизированную команду. Достаточно статической
  таблицы по `kind` из `JpegGlitchOperation` с проверкой полноты в TypeScript.
  Это убирает ветки отказа при регистрации встроенных типов и метод
  `OperationRegistry.validateParameters`, у которого нет вызовов. Универсальный
  `apply(state, parameters, context)` и генератор случайных чисел можно убрать с
  пути планирования после перевода тестов на реальные JPEG-операции.
  [Типы операций](../src/operations/jpeg-glitch.ts#L37) ·
  [Создание реестра](../src/application/jpeg-document.ts#L147)
- Хранить неизменяемую типизированную запись с ID и признаком включения. История
  хранит порядок и снимки для Undo/Redo. Worker получает исполняемый план.
  Каждое добавление сейчас копирует накопленный массив через spread. План можно
  собрать одним проходом. Сейчас `applyCoefficientGlitchOperation` дважды
  переводит маску в JSON, а панель истории читает параметры по строковым ключам
  и перепроверяет точки даже в свёрнутой панели. Сериализовать запись на границе
  `.jpglitch` по актуальной схеме.
  [Добавление эффекта](../src/application/jpeg-document.ts#L434) ·
  [Чтение маски в панели](../src/ui/operation-history.tsx#L181)
- Свести проверку оболочки `OperationRecord` к одному парсеру. Сейчас похожие
  правила для ID, версии, seed и метаданных есть в схеме стека, восстановлении
  истории и сохранении проекта. Штатный путь сохранения использует `.jpglitch`.
  Функции `parseOperationStack` и `serializeOperationStack` вызываются тестами.
  Проверить сохранение и повторное открытие проекта в новой схеме и понятную
  ошибку для неподдерживаемой версии.
  [Схема стека](../src/operations/schema.ts#L177) ·
  [Восстановление истории](../src/operations/history.ts#L49) ·

- Хранить состояние расчёта вместе с запросом. Пересчёт сейчас переписывает

  Apply и Undo `inputRevision` неизменной операции прошёл 0 → 1 → 0 при росте
  ревизии документа. Текущие метки `applied` и `queued` панели выводятся из

### Маска кисти и геометрия DCT

- `createBrushMaskFromStrokes` создаёт по форме для каждого отрезка движения.
  Выход указателя за край и возврат создают несколько отрезков в одном жесте.
  Оверлей умеет их рисовать, а валидатор допускает ровно одну форму. На
  JPEG-фикстуре маска из двух отрезков давала покрытие на сетке и отклонялась
  при Apply и Save. Сразу можно собрать один brush через
  `createBrushMask(strokes.flat(), …)` с общим лимитом точек. Сегменты нужны
  жесту, чтобы пропустить интерполяцию при возврате на изображение. В новой
  схеме достаточно одного прямоугольника или кисти вместо массива `shapes` с
  постоянным `mode: "add"`. Проверить выход за край, оба режима покрытия, Apply,
  восстановление маски и открытие проекта.
  [Разбиение жеста](../src/App.tsx#L2596) ·
  [Создание маски](../src/document/masks.ts#L298) ·
  [Проверка формы](../src/document/masks.ts#L225)
- Проверять границы Block Repeat по исходному и последнему блоку. При постоянном
  шаге промежуточные координаты монотонны по каждой оси. Сейчас предварительный
  обход повторов есть в приложении, Worker и C. Сравнение двух проверок в
  TypeScript совпало на 31 104 комбинациях. Цикл фактической записи остаётся в
  кодеке. Проверить крайние координаты, отрицательные шаги и отсутствие
  частичных изменений при ошибке.
  [Проверка Repeat](../src/operations/jpeg-glitch.ts#L219) ·
  [Проверка в Worker](../src/jpeg/coefficient.worker.ts#L257) ·
  [Проверка в C](../src/jpeg/codec/coefficient-bridge.c#L494)
- Вычислять видимую геометрию компонента один раз и использовать её для
  привязки, отображения и масок. Прямоугольный расчёт порога 50% может обходить
  только пересекаемые строки и столбцы. Его результат совпал с полным обходом на
  5800 прямоугольниках. Для Worker нужны оба правила покрытия — любое
  пересечение и порог 50%. Для нечётных размеров различать видимую сетку DCT и
  ёмкость с учётом дополнения MCU.
  [Размер сетки](../src/jpeg/block-geometry.ts#L244) ·
  [Порог 50%](../src/jpeg/block-geometry.ts#L687) ·
  [Ёмкость MCU](../src/jpeg/inspect.ts#L752)
- Сделать политику покрытия явным аргументом общего расчёта. Оверлей кисти
  сейчас отмечает блок при любом пересечении, а Shift и Shuffle требуют 50%
  площади. В изолированной проверке точка с радиусом 2 отметила блок в оверлее,
  а операция пропустила его. Зафиксировать оба результата в тесте перед
  извлечением общего расчёта. [Оверлей кисти](../src/App.tsx#L375) ·
  [Маска Shift и Shuffle](../src/jpeg/coefficient.worker.ts#L623)

### Один владелец переходов состояния

`App.tsx` держит оба стека истории, копии снимков и доступности Undo/Redo,
байты, URL предпросмотра и несколько контроллеров. При открытии, изменении
истории и Reset повторяются сбросы полей. Проверка терминальной фазы Scan
Corrupt выполняется в нескольких местах. В `updateHistory` есть защитная ветка с
`undo()` после уже выполненной команды. [Загрузка](../src/App.tsx#L1868) ·
[Изменение истории](../src/App.tsx#L1950) · [Reset](../src/App.tsx#L3294)

- Дать существующей сессии документа один набор команд `apply`, `setEnabled`,
  `move`, `remove`, `undo`, `redo`, `reset`. Применение и замена последней
  стадии Scan Corrupt проходят через ту же сессию. Сессия проверяет переход до
  мутации и отдаёт снимок для действующих обработчиков интерфейса. Отдельные
  Worker отвечают за обработку коэффициентов и энтропийного скана. Подтверждение
  стадии Scan Corrupt зависит от результата её Worker, а результат декодирования
  браузером обновляется отдельно. [Вызовы Undo/Redo](../src/App.tsx#L3618) ·
  [Воспроизведение стадий](../src/App.tsx#L3450)
- У каждого расчёта должен быть один владелец отмены до завершения декодирования
  и публикации результата. Проверять актуальность после каждого асинхронного
  этапа. Сейчас при открытии проекта флаг кодирования устанавливается по числу
  записей, а эффект выходит по числу активных команд. Отдельный сценарий для
  теста — Reset или смена файла при ожидающем `Image.decode()` после Scan
  Corrupt. Контроллер очищается до этого ожидания, и старый результат может
  обновить предпросмотр. Метод `PreviewCoordinator.run` вызывают тесты. В
  приложении используется последовательность `begin` / `isCurrent` / `cancel`.
