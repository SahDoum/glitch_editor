# Decision records

## ADR-001: Browser-only application foundation

- **Status:** Accepted
- **Date:** 2026-11-05
- **Context:** Milestone 0 requires a runnable TypeScript application and a deployable frontend without image uploads. The architecture recommends a browser UI and isolates JPEG processing behind later modules.
- **Decision:** Use React + TypeScript + Vite. Treat Node.js as a development/build/test prerequisite only; production output is static browser assets. Use Node.js 20.19+ with 20.20.0 locally and Node.js 22 in CI. Pin direct dependencies and commit the npm lockfile.
- **Consequences:** Local development requires Node.js and npm, but deployments need no Node server or backend. React is included in the browser bundle. No JPEG codec or binary parser is chosen in this milestone.
- **Alternatives considered:** A framework-free TypeScript DOM application would reduce runtime bundle size but would depart from the architecture's recommended React UI. A server-backed implementation is outside the product's local-first privacy model.

## ADR-002: Milestone 1 JPEG inspector capability

- **Status:** Accepted
- **Date:** 2026-11-05
- **Context:** The product specification grouped coefficient inspection with the first JPEG-inspection milestone, while the implementation roadmap defers codec evaluation and coefficient access until Milestone 2. No production JPEG codec has been selected.
- **Decision:** Milestone 1 inspects marker/frame/scan metadata for 8-bit baseline sequential Huffman JPEGs with one interleaved scan and one or three components. Decode the preview using the browser's image decoder, keeping the pixel preview separate from the original bytes and parsed JPEG structure. Defer coefficient-array inspection until the codec evaluation milestone. Limit input files to 50 MiB, image dimensions to 40 megapixels, and marker entries to 10,000; run marker parsing in a cancellable Web Worker.
- **Consequences:** No codec or parser dependency is introduced. Progressive, arithmetic-coded, non-8-bit, multi-scan, and over-limit JPEGs are rejected with a user-facing diagnostic. A successful browser preview is not treated as coefficient access or proof that the JPEG structure is supported by this application.
- **Alternatives considered:** Select and integrate a coefficient-capable codec during Milestone 1. This would conflict with the roadmap's codec evaluation gate and require a dependency/architecture decision before the evaluation work.

## ADR-003: Milestone 2 coefficient-access prototype

- **Status:** Accepted for prototype; not a production codec decision
- **Date:** 2026-11-05
- **Context:** The selected JPEG subset needs access to quantized DCT coefficients. Browser pixel decoders do not expose those coefficients, and coefficient access must remain separate from the decoded preview and original bytes.
- **Decision:** Use `@ai-ecoverse/wasm-libjpeg-turbo@3.2.0-2` as a build-time static library (upstream libjpeg-turbo 3.2.0). Link a small C bridge that calls `jpeg_read_coefficients()` and reads one selected 8×8 `JBLOCK` through libjpeg's virtual-array access API. Run decoding in a dedicated Web Worker. The prototype is read-only and supports only files that pass the existing 8-bit baseline sequential Huffman, grayscale/three-component, single interleaved scan inspector.
- **Evaluation:** The selected package is 320,295 bytes compressed and 1,463,157 bytes unpacked; those numbers describe its npm package, not the final browser module. It was published 2026-11-02 and packages upstream libjpeg-turbo 3.2.0 (the upstream project publishes newer 3.x releases independently). The package contains Emscripten WebAssembly static archives and headers, no ready-made coefficient JavaScript API. Its declared license is IJG, BSD-3-Clause, and Zlib; comply with the upstream notices and include the IJG attribution in product documentation. The bridge was built with Emscripten 4.0.23 without SIMD. Generated assets are 33,281-byte JavaScript and 105,948-byte WebAssembly files; gzip sizes are 10,657 and 41,405 bytes. The browser downloads the codec lazily when coefficient inspection is requested.
- **Native reference check:** The bridge compiled against local libjpeg-turbo 3.0.4 and matched `jpegio` 0.2.8 on all 37 coefficient blocks across five synthetic fixtures (4:2:0, odd-dimension 4:2:0, 4:2:2, 4:4:4, and grayscale). This validates coefficient ordering and block reads against an independent reader, but does not replace building and testing the selected 3.2.0 WebAssembly archive.
- **Alternatives considered:** `@crossbind/port-jpegturbo-wasm` 2.0.0-beta.67 exposes `jpeg_read_coefficients()` through generated bindings but returns an opaque coefficient-array handle; inspecting a block still needs an additional binding. Its package is 1,267,770 bytes compressed and 5,338,713 bytes unpacked. `@cornerstonejs/codec-libjpeg-turbo-8bit` 1.2.8 is a ready-made browser module but its demonstrated API only decodes pixels, not quantized coefficients (637,114 bytes compressed; 2,686,773 bytes unpacked). The smaller static-library package plus a narrow bridge is the more direct coefficient path and adds no production JavaScript codec dependency.
- **Browser verification:** The generated WebAssembly module loaded in the production preview and read/displayed one selected 8×8 block from the synthetic baseline 4:2:0 fixture in a Web Worker. No browser console errors or user-facing errors remained after exporting `HEAPU8` for the worker bridge.
- **Consequences and limits:** This is a prototype, not a production codec or encoder choice. Coefficient access temporarily retains libjpeg's coefficient arrays in WASM memory and rejects images requiring more than 128 MiB of coefficient storage. It does not write coefficients, encode JPEGs, support progressive/arithmetic/multi-scan/non-8-bit JPEGs, or replace the browser pixel preview. The imported source bytes are copied before transfer and remain immutable. Broader browser/process compatibility and independent-reference validation of the generated WASM artifact remain future work.

## ADR-004: Milestone 3 document and operation model

- **Status:** Accepted
- **Date:** 2026-11-05
- **Context:** The editor needs non-destructive document state and repeatable operation history before coefficient-writing and encoding are available. The current coefficient bridge is read-only and exposes one selected block.
- **Decision:** Store original JPEG bytes in a private `OriginalAsset` buffer and expose only defensive copies. Represent the editable document as immutable revisioned snapshots. Keep selection in image-pixel coordinates and spatial masks as a versioned spatial representation. Register typed operations by exact type/version; replay enabled operations from the initial editable representation after edits, toggles, deletion, or reordering. Store immutable frames for undo/redo and use monotonic document revisions to reject stale previews. Version the serialized operation stack independently from each operation definition. A supplied unsigned 32-bit seed drives deterministic random execution.
- **Initial operation:** The UI registers a spatial-mask operation so mask history, parameter editing, enable/disable, reordering, undo/redo, and reset are demonstrable. This operation changes only the editable spatial-mask state; it does not edit JPEG coefficients or pixels.
- **Consequences and limits:** Unknown schema or operation versions are rejected; no migration path is claimed yet. The preview coordinator drops results superseded by a newer request or document revision, but this milestone has no coefficient preview worker to connect. DCT operations, JPEG re-encoding, brush-mask rasterization, and project-file persistence remain outside this milestone. Original bytes are recoverable at all times.

## ADR-005: Milestone 4 coefficient editing and JPEG re-encoding

- **Status:** Accepted for the current supported JPEG subset
- **Context:** Milestone 4 needs an actual JPEG-domain operation, a preview generated from edited coefficients, and an export path. The existing libjpeg-turbo WebAssembly bridge already reads quantized coefficient arrays. The implementation must not silently replace coefficient editing with a decoded-pixel filter or add an unreviewed codec dependency.
- **Decision:** Extend the existing C bridge and dedicated worker to edit the coefficient arrays returned by `jpeg_read_coefficients()` and write a new JPEG with `jpeg_write_coefficients()`. Use a versioned operation that zeros selected AC coefficients for one component and a selected natural-order frequency band (`u + v`); preserve DC. Replay enabled operations from the immutable original for every encoding request. The spatial mask remains in image-pixel coordinates and is mapped to visible component DCT blocks using image dimensions and sampling factors.
- **Codec and build:** Continue using the pinned `@ai-ecoverse/wasm-libjpeg-turbo@3.2.0-2` static library at build time; add no dependency. Keep the existing `npm run build:jpeg-codec` Emscripten 4.0.23 build flow and lazy-load the generated browser module. The choice reuses verified coefficient access and supports coefficient-preserving transcoding without introducing a second JPEG implementation. A pixel-only filter is not an alternative for this operation.
- **Encoding and metadata:** The output is a newly encoded JPEG, not the original entropy stream. Critical JPEG parameters and coefficient arrays are passed through libjpeg-turbo. Saved APP/COM markers are copied except APP0 and APP14; the codec may generate its own JFIF APP0. Arbitrary metadata preservation is not guaranteed. The UI explicitly labels the preview as re-encoded, retains the original byte asset, and exports a separate edited JPEG.
- **Supported subset and limits:** Continue to accept only 8-bit baseline sequential Huffman JPEGs with one interleaved scan and one grayscale or three-component frame. Progressive, arithmetic-coded, multi-scan, and other unsupported inputs remain rejected. Input and output are limited to 50 MiB, coefficient storage to 128 MiB, and worker DCT work is bounded. The operation targets quantized DCT coefficients, not pixels, MCUs, or entropy-coded bytes.
- **Validation:** Unit tests cover frequency bands, masks, sampling-aware block coverage, operation replay, and undo/redo. Native bridge outputs for the synthetic grayscale, 4:2:0 (including odd dimensions), 4:2:2, and 4:4:4 fixtures were opened by ImageMagick and macOS `sips`; source bytes were checked unchanged. The WebAssembly bridge was built with Emscripten 4.0.23 and exercised in a browser for import, mask, coefficient edit, re-encoded preview, and undo/redo.
- **Consequences and limits:** Re-encoding can change file bytes and may discard or regenerate metadata even when pixel dimensions and critical coding parameters are retained. The initial operation zeros AC frequency bands; other coefficient operations are added in Milestone 5. Progressive JPEG and entropy-stream manipulation remain out of scope.

## ADR-006: First Glitch Lab and experiment-first acceptance

- **Status:** Accepted
- **Date:** 2026-11-05
- **Context:** The original Milestone 5 framed quantization and block work primarily around controlled, compatible JPEG output. Product direction clarifies that the editor is for photographers to explore visual consequences of intervening in JPEG coding; universal decodability is one mode, not the primary measure of success.
- **Decision:** Rename Milestone 5 to First Glitch Lab. Add coefficient zero/scale/seeded randomize, DC offset, AC inversion, frequency isolation, explicit DC/AC targeting, in-component block duplicate/repeat and seeded whole-block permutation, plus editable 8×8 DQT patterns. Block permutation uses seeded Fisher–Yates over whole quantized 8×8 blocks including DC, with no block loss or duplication; the mask selects blocks at 50% coverage or greater. Rectangle coverage is computed geometrically, while brush coverage uses deterministic 8×8 spatial sampling. Keep edits in the existing versioned operation history and replay them from the immutable original. Preserve encoded output bytes when browser preview decoding fails, and make the output exportable. Keep entropy-stream/raw-byte corruption separate for Milestone 8, after the newly prioritized usability milestone.
- **Quantization semantics:** Offer `reinterpret`, which retains quantized coefficients and writes the edited DQT, and `requantize`, which approximates the retained unquantized value as `oldCoefficient × oldQuantizer`, divides by the new quantizer, rounds, and clamps to baseline coefficient ranges. Neither mode restores information lost before import. DQT matrices use natural 8×8 order in the UI and coefficient model; JPEG marker serialization remains the codec's responsibility.
- **Compatibility and limits:** The current codec path still accepts only 8-bit baseline sequential Huffman JPEG with one interleaved scan and grayscale or three-component frames. Block repeat and permutation operate on one component's quantized DCT blocks; repeat validates every destination, while permutation preserves the selected block multiset and shuffles DC and AC together. Neither operation copies an MCU or entropy-coded bytes. Component IDs alone do not guarantee Y/Cb/Cr semantics, so UI labels describe the conventional IDs as likely rather than authoritative color metadata.
- **Validation:** Add parser tests for DQT zigzag-to-natural ordering; operation and bounds-validation tests; deterministic DQT pattern tests; operation-history undo/redo and immutable-source tests. The C bridge remains the encoder path; output validity is useful to verify but does not replace checking the coefficient/table changes themselves.
- **Consequences and limits:** This is still a coefficient-domain re-encoder, not a raw entropy-stream editor, and the current codec may reject some extreme coefficient combinations. A failed encode remains an explicit processing failure; a failed browser preview after successful encoding retains the output for export. Metadata preservation remains best-effort. Block swap, multi-block region duplication, local/row/column permutation modes, MCU edits, and arbitrary undecodable stream experiments are deferred.

## ADR-007: Prioritize a coherent tool and selection workflow

- **Status:** Accepted
- **Date:** 2026-11-05
- **Context:** The current tool and inspector layout does not make the active operation or its spatial scope sufficiently clear. Brush and rectangular Select need to work on one visible region, and block inspection needs to be a discoverable canvas interaction rather than a separate command.
- **Decision:** Prioritize a UI usability milestone immediately after the First Glitch Lab and before two-image transplant, entropy-stream experiments, or project persistence. Put grouped tool icons in a top toolbar and show the active tool's settings in the right column. Order that column as the tool panel, History, ORIGINAL ASSET, JPEG INSPECTOR, FRAME COMPONENTS, DQT QUANTIZATION TABLES, BLOCK GEOMETRY, and ENCODED FILE; make the column and each section collapsible.
- **Selection and inspection:** Brush and Select edit one global pixel-space selection that persists when switching tools. Brush paints a continuous region shown as a translucent fill without an outline; rectangular Select keeps its frame. Remove the separate `Add selection mask` action. Inspector selects and highlights a clicked 8×8 DCT block and shows its details in JPEG INSPECTOR; the selected block is distinct from the global spatial selection.
- **Consequences and limits:** This is a UI/workflow priority, not a change to the document representation, selection coordinate space, operation model, JPEG process support, or codec. Tool selection and panel collapse remain presentation/application state; spatial operations continue mapping the pixel-space selection to JPEG units through the existing pipeline. The deferred JPEG milestones retain their scope but move one position later.
