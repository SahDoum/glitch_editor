# Проверка codec lifetime и контрольной точки

Дата: 2026-11-20. База: `e497517`; Node `v24.22.1`, поставляемые
`public/codec/libjpeg-coefficients.{js,wasm}` без пересборки. Это инженерный
замер, а не обещание задержки UI: параллельно работали другие задачи, CPU и GC
не изолированы. Измерения загрузки ниже относятся к созданию WASM-модуля в
Node, не включают сетевую загрузку и запуск браузерного Worker.

## Воспроизведение

```sh
npm run benchmark:codec
# Для большого JPEG, путь относительно корня репозитория:
npm run benchmark:codec -- work/codec-benchmark-4000x3000.jpg
npm run test:worker
# Проверка уже собранного сайта, например под GitHub Pages:
npm run build -- --base=/refactor-smoke/
npm run test:worker -- --built --base /refactor-smoke/
```

`test:worker` требует установленный Chromium (`CHROMIUM=/path/to/chrome` при
другом имени). Протокол Chrome DevTools работает через pipe, дополнительных
npm-зависимостей нет. В CI выбран `google-chrome`, поставляемый образом
`ubuntu-latest`. Отсутствие или сбой браузера завершают smoke-тест ошибкой.

Большой источник для приведённого замера создан локально; он не добавляется в
репозиторий. Команда генерации в использованной среде (Pillow и NumPy):

```sh
mkdir -p work
python3 - <<'PY'
from PIL import Image
import numpy as np
y, x = np.mgrid[:3000, :4000]
a = np.empty((3000, 4000, 3), dtype=np.uint8)
a[:, :, 0] = (x * 7 + y * 3) % 256
a[:, :, 1] = (x * 3 + y * 11) % 256
a[:, :, 2] = (x // 13 * 19 + y // 17 * 23) % 256
Image.fromarray(a).save('work/codec-benchmark-4000x3000.jpg', quality=85, subsampling=2)
PY
```

## Освобождение входа и точное совпадение

После `_coefficient_open` C-мост владеет копией `state.input`, поэтому внешний
буфер `_malloc` освобождается немедленно. Один helper используется для чтения
блоков и кодирования. Проверены 11 синтетических фикстур × baseline/progressive
выход = **22 побайтно совпадающих результата** при раннем и прежнем позднем
освобождении. В большом примере до начала операций освобождается **5 356 648
байт**. Unit-тесты дополнительно проверяют освобождение при ошибке/исключении и
отказ выделения памяти.

## Повторное использование загруженного WASM

Медианы 7 прогонов после прогрева. Операция: AC inversion компонента Y. Размер
маски 320×240 означает 40×30 полных DCT-блоков. Для каждой серии приводится
медиана каждого этапа отдельно, поэтому сумма столбцов может отличаться от
медианы общего времени (оно включает выделения, копии, создание маски и cleanup).

| 1 | 320×240 | новый | 7.351 | 72.702 | 0.626 | 75.142 | 192.391 |
| 1 | 320×240 | повторный | 0.001 | 55.557 | 0.497 | 64.337 | 123.777 |
| 1 | всё | новый | 4.866 | 63.593 | 46.998 | 65.761 | 184.882 |
| 1 | всё | повторный | 0.001 | 53.205 | 46.447 | 61.648 | 162.804 |
| 24 | 320×240 | новый | 4.425 | 66.505 | 11.757 | 65.128 | 163.657 |
| 24 | 320×240 | повторный | 0.001 | 54.365 | 11.858 | 63.185 | 131.719 |

Разницу общего времени нельзя целиком приписывать повторному использованию
WASM: например, применение тех же 24 команд измерялось при различной нагрузке
CPU. Прямой измеренный выигрыш на создании модуля — примерно 4–7 мс в этой
среде. Для маленькой маски преобладают чтение и запись; для длинного полного
стека — повторное применение.

Браузерный прототип использует один **собранный Worker** для двух одинаковых
baseline-запросов и одного progressive-запроса. Baseline-байты совпали, после
каждого результата Worker заново открывает JPEG для проверки всех 64
коэффициентов перенесённого блока. В одном smoke-прогоне кодирование занимало
3.6 мс (первый baseline), 0.7 мс (повторный baseline), 1.6 мс (progressive).
Это маленькая фикстура и единичные наблюдения, не стабильный benchmark.

## Почему прямой checkpoint пока не включён

На одном открытом источнике текущий ABI вернул:

```text
_coefficient_encode(0) → 0
_coefficient_encode(1) → -1
```

`coefficient_encode` вызывает `jpeg_finish_decompress`, который завершает
жизненный цикл image pools. Значит, сохранение одного Worker само по себе не
сохраняет пригодные для следующей записи коэффициенты. Экспортов снимка и
восстановления коэффициентов/DQT нет. Добавление прямой контрольной точки
требует нового жизненного цикла C-моста, пересборки и проверки parity после
каждой операции, Undo/Redo, смены режима и несовпадения префикса плана.

В production оставлен проверенный путь открытия исходника; прямой checkpoint
**не реализован и не заявляется работающим**. Повторное использование готовых
байтов Preview/Apply — отдельная оптимизация владельца сессии. Следующий
эксперимент: отделить encode от финализации decompressor, добавить один явный
snapshot/restore коэффициентов и DQT, затем сравнить full replay с prefix replay.

Оценка одного набора коэффициентов большого примера — **36 032 000 байт**
(34.36 MiB), без allocator overhead. Snapshot + рабочая копия потребуют ещё
один такой набор. Наблюдаемый размер линейной WASM-памяти — 64 MiB; это размер
кучи, **не измерение пикового занятого объёма**. Лимиты остаются 256 MiB для
коэффициентов и 512 MiB для WASM. Browser peak memory для будущего checkpoint
пока не проверена.

В среде нет `emcc` и native заголовков libjpeg. Поэтому подготовка индексов DCT,
обход только затронутых блоков внутри C и C-проверка Repeat по концам не
включались в production без пересборки и проверки. Измерение 1263 мс на
24 полноразмерных операциях подтверждает приоритет последующего эксперимента,
но не доказывает ускорение конкретного ещё не измеренного алгоритма.

## Декодер и сборка

- `npm test -- tests/unit/codec-input.test.ts tests/unit/progressive-jpeg.test.ts`:
  35 passed, 6 **явно пропущены** без `JPEG_INDEPENDENT_DECODER`.
- С временным адаптером Pillow, который читает stdin и пишет PNM в stdout,
  `JPEG_INDEPENDENT_DECODER=... npm test -- tests/unit/progressive-jpeg.test.ts`:
  **38 passed** (5 сравнений исходных фикстур и 1 сравнение изменённого JPEG).
  Pillow использует системный libjpeg 6.2; это независимый от поставленного WASM
  декодер. Адаптер — scratch-файл, не зависимость проекта.
- Ошибка явно настроенного декодера теперь бросает исключение; её нельзя
  замаскировать отсутствием сравнения.
- Smoke проверяет Block Transfer, повторный запрос, baseline/progressive и
  versioned JS/WASM URL под непустым базовым путём.
- Из `check` и CI удалён повторный typecheck (он остаётся в `build`);
  `fileParallelism: false` достаточно без `maxWorkers: 1`. Неиспользуемый Logger
  и его тест удалены; политика allowlist-журналирования остаётся в DEVELOPMENT.
